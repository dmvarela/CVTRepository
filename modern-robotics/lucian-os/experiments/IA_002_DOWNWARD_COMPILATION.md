# IA-002 — Downward Compilation and the Economics of Repeated Reasoning

Status: design experiment

## Question

When should Lucian OS stop paying for repeated general reasoning and compile a validated recurrent pattern into a cheaper reusable skill?

The experiment tests the architectural rule:

> **Compile downward when possible.**

The economic version is:

> **Do not repeatedly spend general reasoning on structure that has become sufficiently stable, bounded, and verifiable.**

The key word is **sufficiently**. IA-002 must also identify regimes where compilation is premature, brittle, or unsafe.

---

## Competing strategies

### A — reason every time

For each recurrence of the task:

```text
new input
-> frontier reasoning
-> execute / answer
-> verify
```

Advantages:

- adapts to novelty each time;
- minimal compiled-skill maintenance;
- fewer stale-policy risks.

Costs:

- repeated frontier tokens;
- repeated context reconstruction;
- repeated latency;
- repeated verification burden.

### B — fixed specialist every time

```text
new input
-> specialist / lower tier
-> verify
```

This is cheaper per attempt but may suffer retries or competence gaps.

### C — reason, validate, compile, audit

```text
first recurrences
-> frontier reasoning
-> preserve examples / provenance
-> verify outcomes
-> infer recurrent transformation
-> bounded validation set
-> compile candidate skill
-> verify candidate

later recurrences
-> compiled skill
-> cheap deterministic / lower-tier execution
-> sampled or risk-sensitive audit

if drift / contradiction detected
-> retract skill eligibility
-> return to reasoning
-> repair / revalidate
```

The compiled skill is not treated as truth merely because it was generated by a stronger model.

---

## Candidate workload

Use a repeated structured transformation with occasional edge cases.

Example:

```text
incoming document
-> recognize a stable naming / extraction convention
-> produce a bounded structured record
-> validate required fields
```

The workload should include:

```text
ordinary cases
edge cases
later distribution drift
```

The exact content is synthetic; the experiment concerns the cost / warrant structure.

---

## Compilation eligibility

A task family should not be compiled merely because it repeats.

Candidate gates:

```text
bounded task scope
stable input / output contract
sufficient validated examples
high observed success
low unresolved ambiguity
known failure conditions
verification method exists
provenance preserved
versioned skill artifact
retraction / fallback path exists
no authority expansion created by compilation
```

A compiled skill inherits the same authority limits as the original execution path. Lower cost does not manufacture broader permission.

> **Truth has to bite.**

## Cost model

Let:

```text
C_F = expected cost of one frontier-resolved recurrence
C_S = expected cost of one specialist recurrence
C_C = one-time cost of discovering + validating + compiling a skill
C_D = cost of one compiled deterministic / low-tier recurrence
C_A = expected audit cost per compiled recurrence
C_R = expected repair / revalidation cost when drift occurs
```

For `N` recurrences:

```text
reason-every-time:
  C_A(N) = N * C_F

compile-downward:
  C_C(N) = C_C + N * (C_D + C_A) + expected drift / repair cost
```

A naive break-even point ignoring drift is:

```text
N* = C_C / (C_F - C_D - C_A)
```

The actual experiment should include failure probability, drift, verification, and revalidation rather than treating this equation as sufficient.

## Tests

### T1 — stable repeated structure

Keep the task distribution stable after an initial learning window.

Expected:

```text
compile-downward eventually crosses a break-even point
frontier-token demand per recurrence collapses
verified completion remains at or above threshold
```

### T2 — premature compilation

Reduce the initial evidence window.

Expected:

A too-early compiled skill should make more mistakes or trigger more revalidation cost.

The system should expose that `compile sooner` is not automatically better.

### T3 — distribution drift

After successful compilation, change part of the input distribution.

Expected:

```text
audit / verification detects contradiction
skill becomes contested or retracted
routing returns affected cases to stronger reasoning
```

A system that keeps executing the old skill after contradictory evidence fails.

### T4 — rare edge cases

Insert a low-frequency case outside the compiled scope.

Expected:

The skill should reject or escalate out-of-contract inputs rather than confidently force them through the known transformation.

### T5 — compilation never pays

Make the task family highly variable or the compilation / maintenance cost large.

Expected:

There should be a regime where `reason every time` remains cheaper or safer over the tested horizon.

This is a required negative control.

### T6 — authority invariance

Compile a transformation whose execution requires a bounded permission.

Expected:

The compiled skill retains the same authority requirement. Repetition and successful validation do not convert permission into ownership.

## Pass criterion

IA-002 supports downward compilation if it identifies at least three distinct regimes:

```text
1. stable + repeated -> compilation eventually pays
2. insufficient evidence / drift -> compilation is corrected or retracted
3. highly variable / short horizon -> repeated general reasoning remains preferable
```

The intended conclusion is not:

> compile everything.

It is:

> **General reasoning should be allowed to create reusable structure when the structure earns that status through evidence and remains corrigible afterward.**

## Architectural interpretation

IA-001 asks:

> Which intelligence tier should solve this step now?

IA-002 asks:

> Should this step continue to require general intelligence at all?

Together:

```text
novel / ambiguous work
-> allocate sufficient intelligence
-> solve
-> verify
-> observe recurrence
-> candidate compression
-> validate
-> compile downward
-> cheap repeated execution
-> audit
-> reopen when reality changes
```

This is one mechanism by which Lucian OS can become cheaper with repeated use without becoming rigid.

A concise principle:

> **Reason where structure is missing. Compile where structure has been earned. Reopen when reality changes.**
